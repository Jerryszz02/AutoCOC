# AutoCOC 桌面界面与离线开发

更新日期：2026-09-24。桌面界面与现有 Python 引擎共用任务、停止规则和报告。完整游戏验收仍按 [ACCEPTANCE.md](ACCEPTANCE.md) 执行。

## 打开与操作

在项目目录双击 [启动AutoCOC.cmd](../启动AutoCOC.cmd)，或运行：

```powershell
.\.venv\Scripts\python.exe -m autococ.gui --config config.toml
# 相同界面的 CLI 入口：
.\.venv\Scripts\python.exe -m autococ.cli gui --config config.toml
```

界面使用 Python 标准库 Tk，不需要浏览器、Web 服务或额外界面包。重新安装本项目后也可使用 `autococ-gui` 入口；已有虚拟环境直接运行以上命令即可。

1. 选择日常循环、村庄维护、仅对战或部落事务，也可勾选自定义任务。连接与启动固定为首项。
2. 设置最多循环、最长运行时间、最低金币与圣水合计、搜索上限和设备地址。其他连接参数由所选 TOML 提供。
   对战策略手动选择：“活动兵两边划”先下活动兵，再把其余普通兵按卡片顺序分两边；“雷龙一字划跟英雄”把普通兵按兵栏顺序沿第一条边铺开，再从中点依次下英雄，不主动开技能。两种打法均选首个清晰对手、缩到最小、不下法术和攻城器，等待结算后回村；资源门槛及胜负不决定流程完成。需要 MuMu 原生通道，策略随方案保存，原资源模式仍可选择。识别不确定会回退完整识别；核验失败不会重放投兵。
3. 默认使用“离线预演”：只生成任务计划与 `dry-run` 报告，不连接模拟器、不启动游戏，不验证具体游戏动作。
4. 游戏更新结束、允许恢复实测后，手动切换“实机执行”再开始。启动界面不会恢复上次的实机模式，也不会自动开始任务。
5. “停止”发送协作式取消信号。已经发出的单次调用等待其自身超时/返回，之后不再发出新的游戏输入；已取得的结果继续写入报告。
6. “历史报告”显示最近 100 份运行报告，区分实机与离线；选中后可阅读原因、收益、打开 Markdown 及查看该报告的原始截图。未知收益仍显示“未知”。

“保存界面方案”写入配置同目录下的 `<配置文件名>.desktop.json`，例如 `config.desktop.json`。采用临时文件加替换写入，不改原 TOML，更不改 MuMu 或 Windows 设置。相对报告、截图和模板路径按 TOML 所在目录解析。

任务在单个后台线程运行，重复开始会被拒绝。关闭正在运行的窗口会先请求停止，保留窗口直到线程结束并尝试保存报告。日志框仅保留最近一段显示内容；完整后台日志写入 `reports/desktop-*.log`，正式 JSON/Markdown 仍沿用原报告格式。

## 捐兵代码的实际边界

本轮把流程推进为“扫描聊天 → 打开明确的捐赠请求 → 观察捐兵窗口 → 逐个单位执行并核验”。已写好逐单位执行、延迟重拍、不重复点击、部分收据保留和支出核验逻辑。

**生产识别器目前尚不生成 `donation_view`，真实捐兵仍未实现完整可用流程。** 当前真实运行找到请求后最多打开窗口保存证据，随后以 `donation_layout_unverified` 失败；不会根据臆测坐标点击兵种。之前的“请求找到后立即报告未支持”已改成这个可采样的停止点。

`donation.py` 的离线执行器使用以下归一化观察契约；这是待实现的读取器接口，不是对当前游戏界面字段的已验证描述：

| 字段 | 所需证据 |
| --- | --- |
| `frame` | 必须等于当前截图路径；整体场景必须为高置信捐兵窗口 |
| `request_id` | 同一请求的稳定身份，防止窗口切换或他人请求替换 |
| `filled`, `capacity` | 当前选定类别的已填充及总容量 |
| `own_units` | 可归因于本账号对该请求的捐出数量；不能只用请求容量上涨代替 |
| `gems`, `elixir`, `dark_elixir` | 同一截图中可核验的货币库存 |
| `units` | 已识别单位列表：`id`、基准坐标 `bbox`、`space`、`currency`、`cost`、`allowed`、`enabled` |

只有允许且可用、容量足够、资源足够的圣水/黑油按钮可被选择；宝石按钮始终排除。每次只点一个单位，最多观察三张新图核验个人捐出数量、请求容量及资源支出，宝石必须不变。未核验的点击不重发，未知支出保留为 `null`。每次最多 50 次单位点击，仍受原任务与总运行期限约束。

这些观察字段是否能从实际界面可靠获得，必须在更新后采样验证。如果游戏不提供所需个人贡献证据，应根据实机可用证据调整读取器与验证契约，不能把缺失字段填成默认值以通过测试。`tests/test_donation.py` 全部使用明确的合成观察，不增加真实捐兵次数。

## 更新后的实测顺序

1. 核对客户端版本、目标实例、分辨率与窗口布局，确认更新没有改变旧模板。
2. 在稳定亮屏条件下复测截图与游戏计时，定位之前的慢速问题。
3. 从界面执行一次真实村庄维护，验证日志、界面响应、停止和报告；再验证运行中关闭窗口。
4. 取得其他成员的真实可捐请求及选择窗口，接入并回放捐兵读取器，再做单次真实捐出核验。
5. 验证最新投兵与结算修复，完成一场完整自动战斗，然后按原标准完成连续 10 场、60 分钟组合运行和收益验收。
