# AutoCOC 分批实施计划

状态：**第 0–1 批已开始执行；新版基线、历史试标及各项实际结果见[试点记录](PILOT_BATCH_0_1.md)与[证据索引](../evidence/batch01-20261028/README.md)。第 2–8 批未启动。** 本轮基于 PR #7 合并后的 `0d3a61c`，游戏经用户授权更新至 18.647.5；旧训练与实机记录不作为新版通过证据。

本计划只安排**先做什么、每批交付什么、何时继续或停止**。产品执行和约 30 秒准备期、冻结计划与连续投放的契约见[战前视觉主计划](VISION_AGENT_PLAN.md)；数据类别、人工复核和分组规则见[采集计划](VISION_DATA_COLLECTION_PLAN.md)；模型与正式质量门见[训练计划](VISION_MODEL_TRAINING_PLAN.md)。[整体验收规范](../ACCEPTANCE.md)保持最终门槛，[当前进度](../PROGRESS.md)记录实施事实，[暂停复盘](../PAUSE_REVIEW.md)是调整顺序的历史依据。规划文档不替代运行报告或实际游戏证据。

## 目标、范围与执行原则

完整目标仍是：在已明确支持的环境和编队中，自动完成收集、配兵、请求与捐兵、相关日常目标、选敌和战斗；战前依据关键建筑和阵型选择打法，按冻结计划连续投放，随后核对消耗、结算、回村与资源账本，并通过长期运行及战中增强验收。先完成一套固定编队的可靠战前战术，再接回完整日常与扩展目录，不以首套编队代表全部兼容性。

首个可判定的战术问题是：**能否根据大本营位置和关键防空建筑的分布，提出有依据的进攻方向？** 批次 0 先核对现有模型类别、策略输入和当前客户端，再冻结首轮实际启用类别；缺少足够数据或合法落点时允许拒绝建议。模型训练顺序为建筑 B 在先、场景 S 在后；R/U 战中增强按批次 8 推进。先复用已有采集、训练、评估和运行框架，新增能力只针对具体证据缺口。

每批开始前写清唯一目标、受支持版本/画面/编队、原始数据和成本上限、对照方式、继续或停止条件。代码变更配相应测试；离线问题先用固定样本回放，现场只做有上限的短试验，连续长窗口留给最终验收。连续两轮没有明确改善时停止同一种尝试，检查数据、实现和评价方法后再决定下一轮。每批报告分别列**代码已实现、离线已验证、单场实机已验证、正式验收已通过**，并列出失败、拒识、跳过及剩余范围。失败窗口原样保存，修复后另开窗口，不拼接成功数。

文中标为建议的数量和时长是**开发预算**，可以在开始一批前按实际数据与成本调整并记录理由；它们不降低或替代原有正式数据、模型和[产品验收](../ACCEPTANCE.md)门槛。开发、测试、训练和实机窗口遵循[临时防息屏与防睡眠流程](VISION_AGENT_PLAN.md#101-windows-临时防息屏与防睡眠流程)，任务结束后释放本次请求。

## 批次 0：固定试点与对照

**工作。** 重新确认客户端版本、战斗模式、设备、截图尺寸、视角和当前可用军队；固定一套编队，逐项列明普通兵、法术、英雄、攻城器与技能是否计划使用、是否已支持。盘点现有代码、数据、模型和实机证据，选定一个现有固定打法作对照，并记录搜索费、场次、时长与停止上限。冻结大本营和关键防空建筑是否构成首轮最小类别集合；不能仅凭旧大本营原型已经训练过就宣称类别已可接入运行时。

**交付与出口。** 一页支持范围、场景和军队快照，一份明确的固定打法对照配置，一份数据/代码/证据缺口表及后续每批预算。只有版本、编队、模型类别及输出到策略输入的路径可以具体核查，才开始批次 1。现场发生版本、分辨率、缩放或编队变化时，先记录变化并重定受影响范围，不把新旧结果合并。

## 批次 1：小批采集与数据冻结

**工作。** 复用现有来源绑定、去重、标注、快照和评估工具。先按建议预算选约 **50 个不同阵型**试标，制作建筑类别正反例、边框、遮挡、相似建筑与 `ignore` 的规则；之后按差异和漏检案例补采，每次采集建议最多增加 **30 个不同阵型**，并在启动前设搜索费和时间上限。关键建筑、核心参考、合法部署边界及相机状态分别记录；同一张图可以服务多个任务，但不能重复算独立阵型。

把同阵型的不同截图、跨会话图、同场相邻帧和裁图归入同一 `leakage_group_id`。训练集用于拟合，开发验证集用于选型和调阈值，最终测试组提前预留、封存；看过测试结果再调参，原测试组就不能继续冒充未见测试。正式标签遵守[人工确认和质检规则](VISION_DATA_COLLECTION_PLAN.md#6-标注复核去重和拆分)：AI 预标注与 `agent_visual` 只作原型，不能升格成人工真值。用户暂缓逐图人审时，可完成素材盘点、初标、标签指南和原型实验；正式数据冻结、正式训练与模型准入保持待数据。

**交付与出口。** 含源图哈希、版本、类别、完整标注状态、分组与拆分的快照，试标样张、类别混淆表和明确缺口。试标发现规则冲突、版本不明或组间近重复时，先修标签/分组再扩采。约 50 阵型是诊断预算，正式建筑测试仍需大本营至少 **100 个独立测试阵型**，其他启用关键类另按[模型门槛](VISION_MODEL_TRAINING_PLAN.md#7-验收层次与建议首轮门槛)准备；现有 17 图原型和少量验证图只能用作历史开发证据。

## 批次 2：建筑 B 模型

**进入条件。** 已冻结首轮客户端、编队、建筑类别和分组；开发训练已有足量已确认标签。人工确认不足时只能做原型训练和离线案例分析，不能发布为正式模型。

**工作。** 首先复用一个现有可训练、可导出、可由运行时加载的配置，比较真正改变的因素。建议同一轮数据最多做 **2 次有明确假设的训练**，每次先设 **1 小时**上限并保留可续跑检查点。每轮报告每类 TP/FP/FN、precision/recall、漏检/误检叠图、位置误差、阵型子集及 Windows 推理耗时。训练不改善时，先复核是否缺数据、漏标、视角或类别映射问题，不靠重复跑相同小样本试运气。

**交付与出口。** 可复现的候选模型、数据与模型哈希、独立报告及可读的成功/失败图例。正式准入须满足既有[建筑检测、定位及数据门槛](VISION_MODEL_TRAINING_PLAN.md#7-验收层次与建议首轮门槛)：大本营测试至少 100 个独立阵型、precision 与 recall 均至少 0.98；其他启用关键类至少 50 个测试实例、20 个阵型，precision 至少 0.95、recall 至少 0.90，并报告定位误差。未达到时保留原型和真实错误，不让模型控制投兵；若连续两轮无明确改善，先调整数据方案。

## 批次 3：场景 S 模型

**进入条件。** 建筑方向试点的主要数据问题已定位，避免同时训练 B、S、R、U。场景分类仍是第一版必需能力，先训练 B 不表示取消 S 的原计划。

**工作。** 分别整理主村、军队、搜敌/敌方预览、战斗、结算及与日常有关的场景；未知、弹窗、云层、断线、维护和界面动画单列。优先回放历史失败原帧，按会话/布局分组补足独立数据，评估逐类覆盖、拒识与把阻断场景误判为可操作场景的次数。只覆盖战斗场景的模型只能称为有限范围开发结果，不能算完整日常场景验收。

**交付与出口。** 场景包、混淆矩阵、拒识案例和关键场景的结果表。正式启用遵守[训练计划中的 S 门槛](VISION_MODEL_TRAINING_PLAN.md#7-验收层次与建议首轮门槛)及[全项目 VIS-01/02](../ACCEPTANCE.md#2-需求与通过门槛)。阻断画面发生错误接受、关键场景覆盖不足或新客户端出现未知画面时保持拒识，并先补数据与定位根因。

## 批次 4：方案评价与只读旁路

**进入条件。** 模型可在固定图上给出可追溯的建筑事实，场景/军队/合法部署区能被验证；未过正式数据与模型门时，只能做离线或只读评价。

**工作。** 为同一截图展示关键建筑、候选入口、清边、主力顺序、计划法术/英雄动作及不适用理由。先做少量明确规则，在独立阵型上衡量核心和入口质量。第一层用固定离线图回放；第二层在真实预览中只读生成方案，记录剩余准备时间、候选与拒识，**投兵数为 0**。现有 `--dry-run` 只验证模拟编排，不等于连接设备的旁路；先核对或补齐仅执行准备、不执行投放的受控入口，并为只读搜敌设费用上限。

Jev 只在已经校验的有限候选中选择；先验证本地规则，再单独检查 Jev 连通与选择效果。外部选择不可用后的本地回退另记原因和成绩，不能计作 Jev 选择成功。未配置真实凭据时仍可完成本地与离线工作，凭据不写入文档或报告。

**交付与出口。** 可复核的方案叠图、依据、拒识列表、实际剩余准备时间及旁路零投兵记录。只有[核心/入口独立评价](VISION_MODEL_TRAINING_PLAN.md#7-验收层次与建议首轮门槛)、合法落点、已启用模型质量和准备预算达到原定要求，才允许模型方案进入批次 5 的受控执行。候选不足或过期时停止自动进攻。

## 批次 5：单场与短串行战斗

**进入条件。** 按本场计划要用的普通兵、法术、英雄、攻城器和技能，先核对执行与后验能力；当前部分打法只支持部分动作，缺失项先实现并验证，不能靠缩减报告称为全军完成。模型、布局、编队及合法边界符合批次 4 条件后，再使用现有 `battle-only` 单独试验入口；该入口不会完成完整日常。

**工作与预算。** 第一场只证明完整链路：`识别 → 决策 → 冻结计划 → 连续投放 → 消耗核验 → 结算 → 回村 → 核账`。通过后在同一配置下做 **3 场短串行**，逐场保留识别依据、冻结时间、输入、实际消耗、结算、回村和资源变化。连续投放期间保持零截图/OCR/检测/Jev，仍须达到[主计划的整批速度和停止契约](VISION_AGENT_PLAN.md#93-准备期与默认连续模式验收)。动作不确定、漏兵、识别冲突、未结算或未回村时结束该窗口，保存原失败，修复后另开窗口。

**交付与出口。** 对每场分别报告软件闭环结果、游戏胜负/星数/摧毁率、实际收益；一次游戏胜利不自动证明软件闭环或模型提升。1+3 仅证明受控短流程的重复性，不替代正式连续十场。稳定通过且失败归因已处理后，再进入日常组合和战术对照。

## 批次 6：逐项接回完整日常

每个小批先做独立任务，再进组合队列。局部成功只验收该项，本批总体状态取各项真实结果；无机会时记录 `skipped` 和原因，不能改写为成功。

| 小批 | 工作 | 所需证据与停止条件 |
| --- | --- | --- |
| 6A 收集与核账 | 普通资源读取、气泡、收空、满仓、提示框与容量 | 前后画面、资源/容量账本一致；无法核销就停止归因 |
| 6B 请求与配兵 | 请求增援、军队页核实、方案应用/保持 | 提交确认、冷却和独立军队数量；不确定时不重复提交 |
| 6C 矿石导航 | 铁匠铺视角、矿石余额、返回主村 | 入口身份、读数和回村均成立；定位不足不降低建筑身份门槛 |
| 6D 真实捐兵 | 请求窗口、限制、数量、捐后状态与支出 | 有真实可捐机会才能验收；无请求时保留未验收 |
| 6E 活动与竞赛 | 读取进度、受支持任务执行、奖励和停止条件 | 真实机会与结算证据；只读进度不等于完成任务 |
| 6F 扩展编队 | 按普通兵、法术、英雄、攻城器和其他方案逐批扩充 | 每个新增类别独立验证身份、数量、动作与后验；首套范围不外推 |

**出口。** 形成逐项能力/证据表，稳定任务才能加入最终组合。捐兵机会与人工标注目前都可能影响正式验收；等待外部条件期间推进可独立完成的批次，不反复要求用户提供不可得的机会，也不放弃原有门槛。

## 批次 7：战术对照与最终组合验收

**进入条件。** 战前模型方案和固定打法均可在同一已声明范围内执行，批次 5 的短链路及需要组合的日常子批已有真实证据；正式环境、模型与数据版本、配置和资源口径预先冻结。

**战术价值对照。** 采用同一编队、选敌条件与目标难度分层，让模型方案和固定打法交错运行。建议首轮预算为**模型打法 10 场、固定打法 10 场**，分小批观察；游戏中的同一敌人不能重打，所以只按相近条件比较。逐场保存候选、选择来源（模型、Jev 或本地回退分开）、消耗、结算、回村、星数/摧毁率、金币圣水黑油及搜索/捐兵支出。报告任务闭环率、胜率与净资源产出；差异不清时写“尚未证明改善”，不能把单次胜利归因于模型。

**正式验收。** 在同一待交付版本按[整体验收规范](../ACCEPTANCE.md#2-需求与通过门槛)另开真实窗口：连续 **10/10 场**由软件完成选敌、部署、结算与回村；一次至少 **60 分钟**组合运行，达到规定的战斗、收集、捐兵和请求检查次数；各功能真实成功次数、故障/停止、可复核交付和[资源收益门槛](../ACCEPTANCE.md#4-可量化资源收益指标)分别检查。检查次数不代替捐兵或请求的真实成功。修复前后、不同配置或人工代操作的场次不拼接为同一窗口。

**交付与出口。** 提交对照和正式验收报告，逐项标记通过、失败、跳过与待数据；只有全部适用门槛及证据齐备，才称对应版本通过完整日常和战术验收。有限阵型/编队的试点胜利不外推为全版本、全单位能力。

## 批次 8：战中动态增强

**进入条件。** 战前连续投放和完整日常有稳定基线；选择一个确实需要战中反馈的动作及可观察事件。M7/R/U 仍属完整计划，但不会阻塞第一版战前连续投放的独立交付。

**工作。** 一次只加入一种可验证触发，例如某英雄技能仍可用、已跟踪建筑出现可靠摧毁证据，或主力到达指定区域后补兵/跟法术。按事件采集正反例和相邻帧，确认身份与镜头连续性，先离线验证事件和误触发，再用受控实机验证动作。`R/U` 权重、运行适配和时序证据分别验收；不把预测框、离线训练或 ONNX 一致性当作实际动作成功。

**交付与出口。** 事件级漏触发/误触发、实际动作效果和完整时延报告。沿用[动态模型与真实链路门槛](VISION_MODEL_TRAINING_PLAN.md#7-验收层次与建议首轮门槛)：从发起截图到识别、决策和输入完成的热运行 P95 目标为 **≤0.5 秒**，按动作类型记录失败及最大值。未达标或误触发时该增强保持禁用，战前模式继续按其自身证据评价。

## 首个实际执行切片与状态维护
