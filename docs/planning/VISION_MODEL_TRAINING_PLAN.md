## 1. 为什么拆出本计划

主计划已经规定战前规划、连续投放、0.5 秒完整动作目标和模型分工，但尚缺数据准入、训练配方、导出兼容性和模型级验收步骤。本次补齐这些实施细节，并把“首轮同时积累前戏素材”的新要求落实到数据流程。

训练的是视觉组件：从图像得到场景、建筑及经验证的动态状态。Jev 使用结构化信息和攻略条目选择有限候选；本计划不训练 Jev，不从攻略视频直接学习点击坐标，也不训练一个同时负责识图、战术和输入的大模型。

## 3. 到底训练哪些模型

| 编号与用途 | 第一轮方案 | 输入 → 输出 | 训练/交付顺序 |
| --- | --- | --- | --- |
| S 界面分类 | ImageNet 预训练 MobileNetV3-Small | 完整 UI → 已支持 scene 类别概率；低置信度/小间隔拒识 | 必训，首先导出可加载包 |
| B 建筑检测 | YOLO26n 为候选，YOLO11n 为兼容对照 | 完整截图 → 建筑类别、框、置信度 | 必训；相同数据上比较准确率和 Windows 完整推理耗时，选择一个 |
| R 局部状态 | MobileNetV3-Small，按建筑 ROI/技能卡 ROI 分开输出头和包 | 指定目标/卡片裁图 → 可见完整/受损/残骸、可用/选中/耗尽等概率 | 增强阶段第一项；静态两包可用且时序标签足够后训练 |
| U 英雄/主力位置 | 小型 YOLO 检测器定位英雄；主力先用群体区域与跟踪组合 | 战场 ROI/全图 → 英雄框、主力群体区域、置信度 | 仅在选定前戏/主力触发需要时训练，和 R 共用连续素材 |
| C 卡片身份 | 先评估现有模板与局部 OCR；不足时训练小分类器 | 卡片 ROI → 身份/来源；数量仍独立 OCR | 条件任务，不默认新增一个数字识别网络 |

同一“视觉系统”可以包含上述多个小模型，不要求它们每帧全部运行。S/B 的包现在有运行时入口；R/U/C 的训练管线和标签可以先做，但必须另交 ROI、跟踪、输出 schema 与运行时适配后才称为已接入。

建筑朝向/模式优先用检测后的 ROI 分类或方向头；实际需要、标签够且基线失败时才增加。墙体先使用标注参考评估规则与几何；需要像素分割时，另开轻量分割实验并新增 mask 契约。禁止把方向、路径、血量或最优打法写成“建筑检测框已提供”。

### 3.1 建筑与攻略之间的中间表示

战前从 B 的建筑事实计算 `buildings[]`、`core_regions[]`、关键目标距离、候选入口、外围结构、未知区域。核心价值由策略 profile 指定，多个核心不能简单合并后仍宣称识别了双核心。首轮维持现有单核心聚合的能力说明；另以人工核心参考验证多核心扩展，尚未通过时排除依赖它的模板。

攻略条目存“适用军队/装备、局面条件、前戏目标、主力入口、触发条件、失败分支、证据 URL/时间点”。训练图的建筑真值不包含“必须从六点打”这种战术结论。对可接受的多种入口用集合评价，不以单一作者选择作为唯一正确答案。

## 4. 数据准入与训练环境

### 4.1 训练前的自动检查

按[采集计划](VISION_DATA_COLLECTION_PLAN.md)生成不可变数据快照，执行：

1. 校验源图/标签哈希、版本、尺寸、类映射、坐标范围、复核状态、完整标注与 ignore 处理。
2. 训练/验证/测试在 `leakage_group_id` 上完全分离；裁图、增强、同场视频和重复阵型继承父组。验证和测试不应用随机增强。
3. 输出每类实例数、独立阵型/会话数、外观、模式、遮挡、版本覆盖；缺少某类验证/测试样本不能将该类计作通过。
4. 将范围外、未知、旧版本不明和教程材料单独标记。教程材料可用于开发实验，但本机正式验收只采用受支持环境的独立原图。
5. 冻结 `data_version`、taxonomy、split 哈希、训练目标、验收配置和测试集合。已有 146 张目前未标注，不能直接执行正式训练。

### 4.2 Mac 候选环境与可移植性

工程环境独立于日常助手 `.venv`。项目要求 Python ≥3.12；实施时建立单独训练环境并锁定经过冒烟的 Python/PyTorch/torchvision/Ultralytics/ONNX/ONNX Runtime 版本、预训练权重来源及 SHA-256。不要写一个未实际安装验证的“最佳版本组合”。

在目标 Mac 记录 macOS、芯片、统一内存、空闲磁盘、`torch.backends.mps.is_built()` 和 `is_available()`；MPS 不可用时明确报告 CPU 模式，先做冒烟，不无声切入耗时正式训练。所谓约 128 GB 内存是主计划中的候选信息，本轮未实测，不能据此承诺训练速度。

先用 32 张已复核训练图跑 2 个 epoch，检测 NaN、内存、导出、暂停/恢复和日志。batch 从保守值开始，降低 batch 处理内存问题；记录实际设备与任何算子回退。训练时长设可续跑上限，保存最后 checkpoint、优化器、调度器、随机状态及耗时，不反复从头训练。

Windows 的运行时基线是 CPUExecutionProvider。Mac 训练速度和 Mac 上的 ONNX 结果都不能证明 Windows 速度；最终验收必须在运行游戏的 Windows 设备执行。Mac 保活绑定训练进程生命周期，Windows 遵循主计划第 10.1 节；保活均须有限期限并清理。

## 5. 可复现的首轮训练配方

以下参数是固定首轮实验的起点，可依据训练/验证集调整并版本化；不通过最终测试集选参数。默认种子 42；候选定型后补种子 43、44 检查波动，不承诺不同设备逐位一致。

### 5.1 S：界面分类

1. 按采集计划映射已支持 scene，训练输出不含 `unknown`。某稀有类样本不足时从本次启用名单移除并列为范围外，不能用 1–2 张重复增强伪造覆盖。
2. 输入宽 320、高 192，整图 letterbox，不中心裁剪；RGB、`scale=1/255`、ImageNet mean `[0.485,0.456,0.406]`、std `[0.229,0.224,0.225]`。补边值与现有 `_prepare` 完全一致并写入 manifest。
3. 替换分类头为启用类别数；冻结主干训练头 5 epoch，AdamW、学习率 0.001；再解冻微调最多 30 epoch，学习率 0.0001、batch 32、weight decay 0.0001、验证指标 7 epoch 无改善早停。batch 可因硬件缩小，实际值入日志。
4. 按组采样，限制同场相邻帧权重；类别不均衡时从类别权重或采样权重选一种，避免无依据叠加。轻微亮度/对比度、实际截图压缩退化可试；水平/垂直翻转、大角度旋转、会裁掉按钮的随机裁剪禁用。
5. 最佳权重按验证 macro-F1 与关键类召回共同选择。在单独的验证未知集上扫 `min_confidence`、`min_margin`，同时报告已知覆盖率与未知误接受。阈值无法兼顾时补数据/调整模型，不靠全拒识过关。
6. 导出 `[1,C]` logits。若做温度校准，将其烘焙进图或导出已校准概率；当前运行时没有独立 temperature 字段，不写一个不会生效的 manifest 配置。

### 5.2 B：建筑检测

1. 使用预训练 `yolo26n.pt` 与 `yolo11n.pt` 各建立基线。正式训练只消费已完整标注、处置了 ignore 的样本；以文件版本控制类别表，模型输出索引映射随包交付。
2. 首轮宽高 640×640、letterbox、RGB、scale 1/255、mean 0、std 1、pad 114，batch 8，最多 100 epoch、patience 20；固定 AdamW、起始学习率 0.001、weight decay 0.0005。先做短跑，记录所有框架默认参数，避免两个候选的隐藏默认差异被当模型优势。
3. 首轮关闭翻转、旋转、透视、mosaic、mixup 和 copy-paste；少量颜色/缩放变化须保持标签正确。后续只逐项开启有实际画面依据的增强，对照验证集结果。训练增强不得作用于测试集。
4. 若小建筑召回不足，先审漏标/类别混淆，再比较 960×960；同时检测输出总元素数、候选数和 Windows 耗时。不能只提高分辨率直到超出当前解码器限制。切片推理需要新的 ROI 拼接和坐标验收，不是配置开关即可默认支持。
5. 决策重点是每个关键类别 precision/recall、误认对象、定位与实际耗时；同时按第 7 节独立评估协议记录 mAP50、mAP50–95。在验证集调运行时每类阈值与 NMS，按最终运行配置重新衡量 precision/recall；运行阈值的调整不得改变用于模型比较的 AP/mAP 评估配置。
6. 两候选采用同一数据/拆分/输入和训练预算，选择通过准入且 Windows 较快的一个；差距不明显时优先导出稳定和维护简单的方案。未经实测不宣称 YOLO26 必然更快。

模型对比最多先做“两个骨干×一个尺寸”，只有明确的小目标问题才扩到 960，不做无界超参数搜索。最终测试集只验收已选方案。

### 5.3 R/U：动态能力

先选两个可观察事件做最小闭环：①已跟踪关键建筑有正向摧毁证据；②英雄技能卡是否仍可用。对应标签从第一轮已收集的连续片段提取，不从预测标签自产真值。

- R 建筑 ROI：224×224、MobileNetV3-Small，区分可见完整、可见受损、残骸、遮挡/未知；技能卡另一个头或独立包，避免类别空间混用。训练节奏先复用 S，再按事件组均衡抽样。
- 训练损失只计算确有标注的字段；血条不可见时掩蔽该项。每个片段的相邻帧、正反状态都在同一拆分中。
- 输出“残骸概率”还需与原目标位置、稳定镜头和连续证据结合；`model:type:index` 仅是单帧编号，必须通过匹配/跟踪生成跨帧 ID。
- 英雄/主力 U 仅在策略需要“到达某区/分流”时启用。英雄按身份定位；主力标群体区域和分群，首轮不追求每个兵的精确计数。
- 评估单位为事件/片段，除逐帧指标外报告提前触发、漏触发、延迟分布、身份切换、遮挡错误与误动作。两个连续帧确认会增加等待时间，必须计入响应延迟。
- 动态 ROI 的提取、跟踪丢失和重定位先在离线时序实现；对应 kind/模型包/适配器尚不存在，禁止直接塞进 `scene/` 或 `building/` 并声称可用。

## 6. ONNX 导出与现有程序的精确衔接

以[模型包接口](../MODEL_PACKAGE.md)为当前 schema 权威；本计划不另造一个不兼容的 v1。第一批目录是 `model_dir/scene/{manifest.json,model.onnx}` 和 `model_dir/building/{manifest.json,model.onnx}`。

### 6.1 导出先于长时间调参

冒烟权重就要导出并走真实加载器，验证后才开始正式长训练。先使用静态 batch=1、FP32、固定宽高，导出 opset 以锁定的 Windows ONNX Runtime 能加载为准并记录。导出器在 CPU/eval 模式执行，保留原始 checkpoint；FP16/INT8 是独立候选，不能覆盖原包且自动继承验收。

| 项目 | 必须遵守的契约/风险 |
| --- | --- |
| 输入 | `[1,3,H,W]` float32；BGR 原图在程序内转 RGB；resize、round、padding、均值方差与训练完全对齐 |
| 场景 | `[1,C]` logits 或归一化概率；类别必须是 `SUPPORTED_SCENES` 的子集，顺序与训练一致 |
| 检测 raw | `[1,4+C,N]` 或可接受的转置布局；中心 xywh、每类分数；`format=yolo_xywh_classes`，无 objectness 列 |
| 检测已解码 | `[1,N,6]`，每行 xyxy、score、class_id；`format=xyxy_score_class` |
| 坐标 | 两种检测格式都必须是预处理输入的像素，不能传归一化坐标或原图像素；运行时负责还原 |
| 后处理 | 当前加载器即使收到已解码结果仍执行同类 NMS；需验证密集建筑不被重复抑制。框架称 NMS-free 不代表当前项目链路也无 NMS |
| 上限 | 当前解码器有输出元素总数 600000、max_candidates ≤1000、max_detections ≤300 的边界；导出形状与密集场景都要检查是否超限/截断 |
| 适用范围 | 当前 146 张都是 2560×1440；不要照抄文档示例的 1280×720 范围。基准坐标与原图尺寸分开记录；只声明实际验证过的分辨率/版本/缩放 |

YOLO26 与 YOLO11 的导出选项/默认头可能随依赖版本不同。实施者必须检查实际 ONNX 的输出名称、形状、坐标和分数，选择本表匹配的格式；不能只根据模型名字自动填 manifest。

### 6.2 包元信息与一致性核对

manifest 至少填满代码要求的 `schema_version/kind/client_versions/code_version/data_version/applicability/classes/model_file/sha256/max_frame_age_seconds/preprocess/output/validation`。初始 `validation.status=unvalidated`；有真实报告后才能改 `evaluated` 并写 report_id，仍不等于实战获准。

另附 `MODEL_CARD.md`、环境锁、训练/导出配置、checkpoint 哈希、拆分哈希、每类指标、困难样本报告、依赖与权重许可信息。时效上限按用途和测量确定，战中不能为让慢模型通过而随意放宽。

在 ≥100 张复核验证图上对比 PyTorch 与 ONNX：相同输入张量、相同解码/阈值/NMS，场景决策一致率 ≥99%，任一关键类 precision/recall 降幅 ≤1 个百分点；匹配检测框还原误差 P95 ≤原图长边 0.2%。超差逐例检查预处理、索引、布局与浮点阈值，不能以模型能加载替代一致性。

## 7. 验收层次与建议首轮门槛

本表是**离线候选进入下一阶段的初始设计门槛**，尚非实测结果或已授权自动战斗。T0/T1 在打开最终测试集前写入版本化 acceptance 配置；如支持范围变化要留新版本，不能看见失败后降低标准并追溯宣布通过。数据不足时明确 `insufficient_data`，不计算一个虚假的通过率。

| 层次 | 门槛/报告 | 通过后允许什么 |
| --- | --- | --- |
| 数据 | 所有正式标签已复核；类/坐标/哈希校验通过；拆分泄漏为 0；每类覆盖有统计 | 开始正式训练；不代表模型有效 |
| S 已知界面 | 每启用类测试 ≥50 张、≥10 个组；macro-F1 ≥0.97；关键预览/战斗/结算类 recall ≥0.98；已知覆盖率 ≥0.95 | 进入旁路识别比较 |
| S 未知/阻断画面 | 至少 300 张独立差异未知图，至少 50 个组；误接受成可执行场景为 0；弹窗/断线/维护也单列被误判成可执行场景的次数，要求为 0 | 该有限集合达标；不宣称未来错误概率为 0 |
| B 检测 | IoU=0.5；每启用关键类测试 ≥50 个实例、≥20 个阵型；大本营另需 ≥100 个实例/独立阵型；各关键类 precision ≥0.95、recall ≥0.90，大本营两者 ≥0.98 | 进入布局与候选评价，未满足类不得声明已支持 |
| B 定位 | 真阳性中心误差 P95 ≤原图长边 1%；同时报告框角误差、mAP50–95、各遮挡/外观子集；不能只报平均值 | 只证明检测定位，不证明精确法术落点 |
| 核心/入口 | ≥50 个未见阵型，含偏置/分散/多核心；关键目标集合召回 ≥0.95；可接受入口集合命中 ≥0.90；所有实际输出落点均通过部署合法性检查 | 可评估战前建议；依赖多核心的打法还须相应接口验收 |
| R/U 动态 | 每个拟触发动作 ≥100 个独立正事件、≥300 个独立负事件窗口；事件召回 ≥0.95，导致动作的误触发为 0；按事件报告延迟、漏触发、未知率 | 只进入受控增强验收，不自动开启默认模式 |
| 真实链路 | Windows 实际设备按动作类型达主计划热运行 P95 ≤0.5 秒；保留最大值、超时、失败、拒识、过期丢弃和实际效果证据 | 满足该动作的速度门；实战范围仍按主计划共同选定 |

precision/recall 的误拒识和有效图推理失败不能从分母消失；每类报告 TP/FP/FN、样本组数与置信区间。若拒识过多，即使零误触发也不算可用。关键类缺样本时可继续原型研究，但不进入该类控制的动作验收。

**现有评估脚本仍需补齐的量**：独立评估路径的 AP50/mAP50–95、P95 定位误差、分组/子集统计、核心/入口与事件指标、准入判定器。现有 `evaluate()` 从 `BuildingModel.detect()` 获取已按 manifest 置信度阈值过滤、经 NMS 和候选/检测数量上限截断的结果；因此当前 AP50 是运行配置下的截断统计，不能直接复用为模型比较或正式 AP/mAP 验收依据。实施时明确分开：

- AP/mAP：使用运行阈值过滤前的原始预测，或独立且足够低的评估置信度下限，保留构建完整 precision-recall 排序所需的预测。评估下限、NMS/去重规则、候选与检测上限单独配置，在模型比较前冻结并随报告版本化，不读取运行时阈值或沿用实时链路的限额。先在验证集检查降低下限、提高上限后的 AP 稳定性，并报告截断情况；导出图内已做过滤或 top-k 截断且无法满足评估协议时，必须交付兼容的评估导出，不能从已丢弃的结果恢复完整 AP。
- 运行点指标：继续通过真实 `BuildingModel.detect()`，使用最终 manifest 的每类阈值、NMS 和数量上限，报告 precision/recall、定位与耗时；这些指标反映实际部署配置，和独立 AP/mAP 分开列出。
- 两条路径只共享 IoU 与同类一对一真值匹配实现，AP/mAP 的匹配按置信度排序并在各 IoU 阈值下独立重置；不共享运行过滤后的预测列表。回归须覆盖：同一原始输出/真值且评估配置固定时，仅改变运行阈值不会改变 AP/mAP；低分真阳性、重复框、密集场景截断、匹配规则及推理失败分母处理正确。

脚本返回 0 不作为这些门槛的替代。现有建筑评估 JSONL 没有 ignore 语义：首批使用完整复核的可评估图/区域；含不确定目标的困难集合另报，或先实现并测试 ignore 匹配，不能删掉不确定框后将该集合冒充完整真值。

### 7.1 速度的统计边界

分别记录模型加载、首次推理、预热后推理、ROI/解码/后处理、完整战前准备与“取帧请求至输入结束”。在 Windows 上至少用 200 张差异图做模型热运行统计，真实动作样本量在有限实测前单独约定，不由离线样本数授权自动刷战斗。

另报事件发生至下一帧采到的观察等待，以及事件至输入结束的响应；5 帧/秒采样本身最多约 200 ms 的理想采样等待，实际还会有抖动，不能从报告中删除。多帧确认、网络 Jev、切卡和整个动作组均在对应链路里统计，不相加不同实验的中位数宣称整体达标。

战前由 Jev 选择模板/候选并准备分支，战中紧急动作优先由本地已验证条件触发，只观察当前阶段需要的 ROI。需要 Jev 重新判断时有独立期限并丢弃迟到结果。连续投放模式仍不插截图；状态驱动前戏属于增强模式，要单独验收。
