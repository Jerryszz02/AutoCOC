# 日常助手：任务、目标与打法

日常助手按勾选顺序执行收集资源、请求增援、部落捐兵、刷资源、刷活动和部落竞赛。连接、检查军队、结算和回村由任务内部处理。每个对战任务保存自己的打法、筛选条件、目标和战斗/时长/搜索上限。当前范围是 Windows + MuMu 的主世界；部落战、建筑大师基地和都城不在本流程内。

## 从界面开始

在项目目录运行 `./启动AutoCOC.cmd`，或：

```powershell
.\.venv\Scripts\python.exe -m autococ.gui --config config.toml
```

「运行」页左侧勾选并调整任务顺序。任务旁的「设置」会打开「配置」页并定位该任务。配置页设置设备、预演/实机模式、回村维护间隔，以及各对战任务的独立参数。资源筛选开关和金币、圣水、黑油、金币＋圣水门槛采用同时满足的规则；关闭筛选时才不按资源数过滤。刷资源可填写库存数值目标或勾选满仓目标；满仓必须读到库存及容量。活动和竞赛要选适配文件，竞赛仅执行已接受的任务，不会自动接取、放弃或替换。

配兵数量和打法步骤目前在配置页的 TOML 文本编辑器中修改，支持加载、校验和保存；没有图形化配兵表或步骤编排器。设备地址为手动输入，活动与竞赛适配器使用文件路径。

打开界面不会连接或操作游戏，也不会恢复上次的实机模式。先用默认的「离线预演」确认任务顺序和配置；需要操作游戏时再手动选「实机执行」。运行中「停止」发送协作式取消信号，等待当前有时限的调用返回，然后保存报告。配置方案存到 `config.desktop.json` 等同名 `.desktop.json` 文件，不改基础 TOML。

右侧分别显示已完成战斗、游戏胜利和目标达成；战斗进度把**库存**与**已核验的累计战斗收益**分开显示。读不清的资源保持「未知」，不会写作 0。详细日志、历史 JSON/Markdown 和原始截图在运行页下方；[桌面操作说明](DESKTOP.md)有更多细节。两张实际窗口截图及哈希清单在本机忽略目录 `reports/gui-daily/`，它们只证明界面可显示，不是游戏动作证据。

## TOML 与命令行

从 [routine.example.toml](../routine.example.toml) 复制任务方案，按本次顺序排列 `[[routine.tasks]]`。每项用不同 `id`，`kind` 取 `collect`、`request`、`donate`、`resources`、`event` 或 `clan_games`；`enabled=false` 会跳过。三个对战任务可同时启用，且各自配置 `strategy` 或 `strategy_file`、`max_battles`、`max_duration_sec`、`max_searches`、`resource_filter` 与 `goal`。`maintenance_interval_sec=0` 表示日常维护只执行一次；设为正数后仅在战斗回村后定期复查已勾选的维护任务。

```powershell
# 只编排并写预演报告；不连接模拟器
.\.venv\Scripts\python.exe -m autococ.cli run --config config.toml --routine routine.example.toml --dry-run
# 每个启用的对战任务最多打一场，覆盖为同一个本地打法文件
.\.venv\Scripts\python.exe -m autococ.cli run --config config.toml --routine routine.example.toml --strategy-file strategies\two_edge.toml --once --dry-run
# 本机确认可用后，去掉 --dry-run 才会连接设备并执行
```

`--routine` 接受 TOML 或 JSON；例子可单独存放在任意目录。任务中的相对打法/适配路径以该**任务文件所在目录**为基准；直接写在 `config.toml` 的 `[routine]` 或桌面方案中的相对路径则以 `config.toml` 所在目录为基准。`--strategy-file` 覆盖该次运行所有启用的对战任务打法；`--strategy` 选择旧内置打法。`--once` 将每个启用的对战任务上限临时改为一场，不改文件。非法打法、适配文件或全未勾选的方案会在连接设备前拒绝。`--dry-run` 仅报告 `simulated`，真实战斗与收益计数保持 0。

### 三种目标

各任务的时长上限在开下一场之前检查，已开始的战斗先结算回村，再报告「达到限额」并切换任务；基础配置的运行总时限和单步超时仍约束整个会话。不要把运行总时限设得比本次任务队列预计时长更短。

基础 TOML 可单独配置 `[battle].settlement_timeout_sec`，控制部署后的结算等待；省略时沿用 `deploy_timeout_sec`，保持旧配置行为。模拟器计时较慢时，可以增加结算等待，同时保留部署动作的较短上限。`runtime.task_timeout_sec` 和运行总时限仍然有效，必须给结算留出余量。

资源任务省略整个 `resource_filter` 表时默认使用金币＋圣水 300,000 门槛；活动和部落竞赛默认关闭资源筛选，可以独立启用。显式写出该表后，未填写的金额条件不启用。例如只写 `min_dark_elixir=9000` 就仅筛黑油，不会暗中附加金币＋圣水要求。界面里留空的金额条件也不启用。

| 任务 | 对手选择 | 游戏进度的完成依据 |
| --- | --- | --- |
| `resources` | 可分别要求金币、圣水、黑油和金币＋圣水最低值；资源未知时不按零计算 | 指定库存达到数值，或在库存与容量都可读时确认满仓；只设场数则达到上限显示「达到限额」 |
| `event` | 可独立启用同样的资源筛选；打法还须符合活动得分条件 | 适配文件识别到当前活动页面、活动进行中标记和实际进度 |
| `clan_games` | 确认已接受的指定建筑任务和目标建筑；首批目标为防空火箭、法术工厂 | 游戏里该已接受任务的进度与总要求一致 |

刷资源设有库存数值或满仓目标时，回村后会有界重拍库存与相关容量，末三帧一致才判断完成与否；持续变化或读数未知会停止，不用回村动画中的瞬时低值再开一场。只设场数限额时不增加这段观察。

[活动适配示例](examples/event.adapter.toml)和[竞赛适配示例](examples/clan-games.adapter.toml)只展示 schema，**不是已校准的真实活动或竞赛**；使用前须依据当前客户端截图修改入口、标题、状态文字和进度区域。竞赛示例中的村庄日历模板、标题「活动」及「部落竞赛」区域内「打开」入口来自一次只读实机观察；实际已接受的建筑任务标题、状态及任务进度区域仍未校准。个人积分如 `3600 / 10000` 不能用作该任务进度。适配器需要明确的页面标题、唯一入口文字或模板、进度区域，以及活动的 `active_label` 或竞赛的 `accepted_label`。可选 `[[navigation]]` 最多三步，每步先核验 `page_title`，可用 `section_label` 与 `section_roi` 锚定区域，再在 `open_roi` 内寻找唯一的「打开/查看/详情」文字。每层返回也先核验上层标题；过渡帧只重拍，不重复点返回。旧适配器不写 `navigation` 时保持单跳。活动还必须声明 `scoring_condition`：`battle`、`destroy_building` 或 `deploy_units`。`destroy_building` 需声明 `building_type` 并配置目标打法文件，缺少时在战斗前报告未支持；`deploy_units` 需列出单位目录中的 `scoring_units`，打法动作要与这些单位匹配。竞赛适配器必须声明 `building_type=air_defense` 或 `spell_factory`。任务未接取、活动结束、页面/数值识别不清、目标样本缺失时会明确报告原因，不把战斗场数充当活动或竞赛进度。

Android Back 有时会越过日历页直接回到村庄；若新帧已核验为村庄，就不再点返回。中间画面不明时只限次重拍，无法锚定则停止。

## 打法与识别边界

建筑模板按客户端版本隔离，实机版本未知或与样本不一致时，建筑目标在搜敌前报告未支持。`scripts/prepare_building_samples.py` 接收人工标注的 JSON：顶层须有独立观察到的 `client_version`，每个建筑变体须有两场独立战斗的存活／摧毁截图、非目标负样本和固定最小缩放证据；脚本校验后才写入素材，拒绝把不同版本合入已有样本库。目前尚无通过该要求的真实建筑条目。

适配器可用 `unavailable_label` 声明游戏中明确的「已结束」或「尚未接取」文字；读到它时按无机会跳过。缺少样本或适配文件报告未支持，状态文字读不清则停止并保留失败证据。三者不会互相冒充。

`strategies/` 中的 TOML 文件示范单边、双边和雷电定点打法；[混合动作示例](examples/mixed-strategy.toml)展示语法。`army_mode="captured"` 使用当前已识别军队；`army_mode="recipe"` 在 `[[army.units]]` 写入稳定 `unit_id` 和数量，并在战前应用及核对。配方相同时跳过修改；仅更改普通兵或法术时优先使用当前军队选择器，逐次核对数量后再继续。保存／编辑页的识别仍不完整，不能据此使用整套已存方案。`[[steps]]` 可按顺序下兵、下英雄、触发英雄技能、下攻城器、施法、等待或结束战斗。英雄部署和技能是两个动作，施法需核对消耗与建筑结果。复杂打法可由本地 Python `planner` 生成动作计划，实际输入仍走共用执行器。

使用 `planner` 时，TOML 的静态 `[[steps]]` 同时声明战前需要的动作能力和建筑目标类型。脚本可按画面重排步骤、调整配方限额内的数量与落点、增减等待；不能新增静态步骤未声明的点击动作、相对施法类别或建筑类型。`target="objective"` 按当前任务配置的目标建筑解析。超出声明的计划会在任何打法动作前拒绝，不会绕过搜敌前的建筑识别与缩放检查。

具名单位默认只从自身军队或活动兵卡定位；要用同名援军须显式写 `source="clan_reinforcement"`。兵卡不在当前视口时，程序只在已核验的战斗底栏内有限次横向滚动，每次等待新视口稳定并重新识别身份和数量；找不到或画面不明就停止，不沿用滚动前的点击位置。当前军队通配符打法仍要求初始完整兵栏和独立军队清单一致，不能靠滚动猜测缺失兵组。滚动查找已有合成帧及当前客户端真实滑动、回弹截图的回归测试；首次实机尝试因视口尚未稳定而在施法前停止，修复后完整的施法与结算仍须实测。

配方中的 `optional=true` 只有在战前完整核验确认自身军队没有该单位时才允许省略对应动作，并在回执中记录原因和核验帧。身份未知的卡、必需单位以及援军不会因此被忽略；所有进攻动作都被省略时也不能计作完成战斗。

配方只精确替换其中声明的**单位类别**：例如只声明雷电法术时，普通兵、英雄和攻城器仍沿用当前军队。游戏的「使用已保存配置」会切换整套军队，因此程序仅在当前与目标的四类身份和数量、英雄宠物与两件装备，以及保存方案相应信息都完整可读且一致时才允许点击「使用」，之后再核对现军队。宠物与装备可以在英雄身份独立识别后比较其图标视觉指纹，无须靠栏位顺序或猜测图标名称。本机四位现役英雄及其 12 个宠物／装备图标已有独立帧核对；这不代表全部英雄已覆盖。本次现役三种攻城器也已有独立身份样本。当前选择器只在整套现军队和英雄负载完整可读时开放差异修改；保存方案与其他单位的编辑样本仍不完整。缺少样本时不会凭兵栏位置、图标外观猜测或覆盖已有保存方案。

当前军队直接修改会先检查所有待改类别的数量、目标卡、可用状态和容量，再先减后加；每次只点击一次并用最多三帧确认，未知或异常数量立即停止。满容量灰卡仅可用于预检，释放空间后必须重新看到可加状态才能点击。当前实现不能经过整类删空的状态，会在任何修改前拒绝。已有保存方案和新复制方案也要检查单位可用状态及容量；住房数未知不按零计算。已明确锁定、过期或超容量时，先确认回村，再按「无机会」跳过该任务；证据不足显示「未支持」，修改后无法核验则停止运行。复制当前军队需要完整的既有方案 ID 清单、空槽的视觉证据，以及复制后新出现 ID 的完整军队回执；灰色兵卡和与当前配兵相同的旧方案均不能当成空槽或新副本。当前保存／编辑页的生产观察尚不足以通过全部检查。直接修改与整套保存方案是不同路径，各自的实机证据见交付记录。

单位目录提供稳定 ID，但**目录中有名称不等于当前客户端画面已能识别该单位**。识别依赖头像/状态样本和当前帧数量，不根据兵栏位置猜兵种、法术或英雄。运行 `autococ.cli capabilities` 可查看单位和建筑覆盖情况；修改前缺少样本会报告未支持，已确认未解锁或过期且未修改军队时核验回村后按无机会跳过，动作后军队核对失败则停止运行，不会盲目落兵。捐兵窗口的生产识别仍缺真实样本，入口保留，不能算已可用。

每场战斗有独立 ID，报告区分 `succeeded`、`failed`、`skipped`、`not_supported`、`limited`、`cancelled`、`simulated`。`succeeded` 的任务数、完成战斗场数、胜利场数和目标达成数口径不同。先前的[两边一字划单场实测](TWO_EDGE.md)证明那次投兵、结算及回村，不证明新目标和连续运行已通过。[完整验收要求](ACCEPTANCE.md)中的连续 10 场、至少 60 分钟组合运行，以及资源、活动、竞赛、捐兵的真实进度证据仍待取得；没有可用活动或竞赛时对应实机验收保留待验证。
