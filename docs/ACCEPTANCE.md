# AutoCOC 量化验收与资源收益口径

验收目标版本：2026-09-22；进度更新：2026-09-24。以下门槛保持不变，当前各项完整要求仍为 **未验收**。已取得的部分现场证据见第 7 节及 [开发进度](PROGRESS.md)；单个任务成功、开发探测、单元测试或 dry-run 都不能替代完整验收。

## 1. 范围和验收环境

目标是 Windows + MuMu 中自动识别、运行游戏、完成对战、收集资源、捐兵和请求增援。功能不能以其中一个成功闭环替代全量交付。

现场验收必须记录：客户端版本、包名、账号对应的匿名本地标识、大本营等级、语言、军队方案、账号联赛/战斗模式、设备 serial、截图尺寸、配置快照的摘要、源码版本或源码文件哈希。账号标识只用于对齐运行，不保存登录凭据。

先核实账号实际模式、军队可用性、资源和仓库容量，再运行任务。无法进入指定模式或游戏有每日限制时，记录环境限制；不得把练习、回放或预制截图当成真实匹配战斗。开发期可以在当前可用配置上迭代；最终报告应明确实际验收配置，不能推断所有分辨率、所有语言和所有军队都受支持。

10 场连续实战是最低验收窗口，不是统计上证明长期 100% 可靠。通过后仍报告更长运行的真实成功率并保留失败。不允许删掉失败后拼接连续 10 场；修复后可以开启新窗口，旧窗口仍保留。

## 3. 结果定义与统计分母

| 状态 | 定义 | 能否计入功能成功 |
| --- | --- | --- |
| `success` | 已产生所需游戏结果，且动作后观察能够证明 | 仅 `live` 模式可以 |
| `failed` | 已尝试但操作失败、超时、场景不匹配或结果不可核验 | 否 |
| `skipped` | 有可靠证据证明当时不存在可执行机会 | 否 |
| `not_supported` | 当前实现缺少必要功能、识别模型或流程 | 否，明确未实现 |
| `cancelled` | 用户或运行限额中断，任务尚未完成 | 否，单独保留 |

未知资源数值用 `null`/未知表示，不用零替代。未知场景、缺少 OCR 或只有旧截图不是没有机会。

每个任务分别统计 `opportunities`、`attempts`、`successes`、`failures`、`skipped`、`cancelled`、`not_supported`，打印分子和分母。已识别可执行机会被无故忽略时，要体现为机会执行率下降。

```text
真实任务成功率 = 已核验 live 成功次数 / 已启动 live 尝试次数
机会执行率 = 至少启动过一次尝试的独立机会数 / 已确认的独立可执行机会数
战斗胜率 = 胜利结算数 / 已核验战斗结算数
识别覆盖率 = 达到接受条件的预测数 / 标注样本数
已接受分类准确率 = 正确且被接受的预测数 / 被接受的预测数
```

已启动尝试的结果必须完整归档；失败后重试算新尝试，不覆盖旧尝试，但不增加独立机会数。重复观察同一条援军请求不算新机会。无尝试时成功率为无样本，不是 100%。包含取消的成功率注明分母；另提供剔除用户取消后的诊断指标时须另起字段，不能替换原始统计。

各任务后置证据：

- 收集：先观察可收集目标，执行后目标消失/已收空且库存增加；容量封顶时记录满仓和目标状态，不能捏造具体入库量。
- 对战：进攻前观测、部署实际生效、真实结算、回到村庄四段齐全；战斗完成与游戏胜利分开。
- 捐兵：先存在适配请求，执行后其已填充容量、剩余容量或捐兵数量变化与动作一致，另存支出依据。被他人同时填满的请求不能只因消失就归功于本软件。
- 请求：提交后出现自己的请求或明确游戏确认，按钮/冷却对应变化；仅关闭弹窗不够。收到回应额外记为 `reinforcements_received`，不是提交成功的必要条件。
- 启动/恢复：目标游戏前台、目标场景及可用入口均得到确认；等待完成不代表恢复成功。

## 4. 可量化资源收益指标

### 初始性能目标

以下是开始迭代的固定目标，不是对未知账号的既得表现保证。同一账号、同一军队、同一模式至少 60 分钟真实组合运行：

1. **战利品加已核验战斗奖励的金币与圣水合计 ≥ 2,000,000 / 小时。** 分项数值也须保留。
2. **扣除已核验捐兵与搜索支出后的金币与圣水合计净经营产出 ≥ 1,000,000 / 小时。** 人工升级/购买的收支单独记录，不能静默抹掉。
3. 黑油产出、捐出和库存净增分别单列 `/小时`；不把黑油乘未经约定的权重并入金币圣水。
4. 可确认的宝石和突袭奖章消耗为 0；请求援军不得变成花费货币自增援。
5. 真实收益不可重复计数；结算截图与原始数值复核 100% 对应。金额缺失导致无法复算时，收益验收不通过。

若账号或模式使目标不适用，记录事实并形成显式目标修订及理由，不能在结果出来后偷偷降低门槛。功能与收益性能是两个维度；达到收益目标不能弥补捐兵或请求功能缺失。

### 分资源账本

对每一种资源 `r`（金币、圣水、黑油）记录：

| 字段 | 含义 |
| --- | --- |
| `storage_start[r]`, `storage_end[r]` | 同一资源栏口径的起止库存 |
| `capacity_start[r]`, `capacity_end[r]` | 起止容量；未知明确标记 |
| `battle_loot[r]` | 结算中的战斗掠夺部分 |
| `battle_bonus[r]` | 另列的已确认战斗奖励；不能把含奖励总额再与奖励相加 |
| `collected_credited[r]` | 收集动作确认入库的资源；无法隔离天然产出时注明估计或未知 |
| `donation_spend[r]` | 真实捐兵支出，由界面单位费用和已确认数量或隔离的库存差确定 |
| `search_spend[r]` | 真实搜索支出，按当前界面核实，不能硬编码旧费用 |
| `other_inflow[r]`, `other_outflow[r]` | 额外奖励、人工操作等非主循环收支，单独标识来源 |
| `capacity_limited[r]` | 是否容量封顶；有独立证据才填满溢损失值，否则记未知 |
| `unreconciled[r]` | 理论收支和库存净变之间尚未解释的差额 |

```text
战斗毛产出[r] = battle_loot[r] + battle_bonus[r]
经营净产出[r] = 战斗毛产出[r] + collected_credited[r]
                - donation_spend[r] - search_spend[r]
库存净增[r] = storage_end[r] - storage_start[r]
每小时指标[r] = 对应窗口资源值[r] × 3600 / 窗口墙钟秒数
```

经营净产出是来源与支出口径，库存净增是实际持有量口径，二者同时展示。确认实际入库、容量损失及其他收支后才能对账；有未知项时不能宣称两者一致。

时间从任务运行开始到停止，包含启动、识别、搜敌、战斗、返回、捐兵、等待和恢复。不得只用战斗动画时长作分母。手动调试/人为暂停保留在记录；可另报告自动运行有效时长作为诊断，不取代墙钟收益。

满仓时仍可核实战利品，但不能用未入库收益证明库存增长。完整收益验收应有足够容量的窗口；满仓窗口保留数据并明确受限，不自动通过净库存检验。不因该指标擅自花费资源升级或购买来制造空间。

## 5. 证据目录与事件格式

以下是目标证据格式，不是宣称程序已输出这些文件；实现可选等价布局，但字段和关联关系不能省略。

```text
reports/<run-id>/
  manifest.json          # 版本、环境、配置摘要、模式与起止时间
  events.jsonl          # 按时间排序的观测、动作、验证和结果
  metrics.json          # 完整计数与分资源账本
  summary.md            # 结果、限制和证据链接
  frames/               # 不覆盖的原始截图和必要裁剪
  review.csv            # 现场人工抽查与标注结果
```

每条任务结果至少可回溯：

```text
run_id, task_id, attempt_id, mode(live/replay/dry_run)
started_at, ended_at, task_name, status, reason
device_serial, screenshot_resolution, source_revision_or_hash
before_frame, after_frame, frame_sha256, observations
actions[{timestamp, kind, target_bbox_or_point, reason, source_frame}]
verification{expected, observed, evidence_frames}
resource_changes{gold, elixir, dark_elixir, costs, uncertainty}
```

每场战斗有独立 ID，同一结算只入账一次。重试、重启、回看已有结算不得重复增加成功和战利品。截图文件名不可复用导致上一轮证据被覆盖。

报告首页直接显示：执行版本、`live/replay/dry_run`、各项真实成功/失败/跳过/未支持次数、实际战斗数、每小时资源收益、停止原因、当前未通过要求。

## 6. 截图识别集与测试边界

- 训练/调参截图与验收截图分开。相邻连拍不能膨胀样本数；至少包含不同布局、数字、请求和正常过渡画面。
- 标注保存场景、数字真值、按钮框、可执行与不允许执行的任务。报告保存逐例预测、混淆矩阵、各类 precision/recall/F1 与误点场景。
- 声称支持额外分辨率/缩放或语言时，要有该配置的独立样本和完整任务验证，不能只靠坐标比例推断。
- 单元测试证明状态机、金额计算、超时、重试和边界行为；截图回放证明静态识别；只有现场任务证明真实游戏交互有效。
- dry-run 不访问游戏，不得产生 `live` 成功或资源增量；测试假结算和假库存必须带模式标记。
